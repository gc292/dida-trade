## 1. Executive summary

The implementation contains functioning Classic, Multi and Fast Paxos coordinators and a coherent implementation of causal local balance reads. There is substantial evidence for the core consensus mechanisms, especially Fast Paxos. **An unconditional correctness/compliance sign-off and progression to paper preparation are not yet justified.**

The audited revision ran **90 tests: 88 passed, 2 failed, 0 errors, 0 skipped**. Both failures are obsolete cached-BALANCE expectations in the Classic/Multi distributed suite, not evidence of conflicting Paxos decisions. Nevertheless, each failure aborts a larger scenario before its leader-change, execution-order and late-payload assertions. Those later assertions therefore did not validate this revision. A comparison execution of the three existing Classic/Multi tests on pre-Step-4 revision `f4876eb` passed all three.

Two shared trading-domain defects were reproduced by evaluating the existing compiled `TradeManager` methods: explicit `populate(5)` after normal startup leaves existing users at balance 10, and percentage arithmetic overflows on legal positive integer values. Source inspection also establishes two failure paths requiring directed reproduction before estimating practical impact: terminal Learn RPC errors have no application-level replay, and Multi can retain an expired retry for an already decided instance and repeatedly run its event loop.

Schedule B correctly contains **five acceptors**, with **Fast decision quorum 4 and recovery quorum 4**. The scheduler extensions exist and are used. These choices satisfy the relevant intersections and course recovery rule; reverting to three acceptors would be wrong.

Step 4's scalar watermark is technically appropriate for a single ordered replicated history. Its implementation must still be exercised through the real client against lagging replicas, including read-to-read dependencies, duplicates and cancellations. None of the existing tests supplies a nonzero `min_version` or asserts the client's watermark. Passing Fast tests therefore does not establish causal-read correctness.

No conflicting decisions generated by the production protocols were demonstrated. No CRITICAL issue was established. This is a source review and finite test audit, not a formal proof or an exhaustive exploration of message schedules.

## 3. Architecture and actual request lifecycle

### 3.1 Components

The seven child Maven modules are `core`, `configs`, `contract`, `util`, `app`, `console`, and `server`; the root aggregator makes eight reactor entries. `contract/pom.xml` generates Java messages/stubs from `DidaTradeMain.proto`, `DidaTradePaxos.proto`, and `DidaTradeMaster.proto`.

`DidaTradeServer.main` selects CLASSIC/MULTI/FAST and registers the main, Paxos and master services. State construction selects a separate coordinator, initializes the domain/history/log/channels, and starts its worker. Fast is restricted to Schedule B. Classic/Multi should be deployed with Schedule A for the audited assignment steps. Schedule flags alone do not select a protocol implementation: immutable `ProtocolMode` does.

`ConfigurationScheduler` delegates membership, leadership and quorum policy. `RequestHistory` stores canonical pending and processed records under synchronized access; pending arrival order uses `LinkedHashMap`. `PaxosLog` holds accepted values, decisions, Fast authorizations and learner certificates. `RequestRecord` is the response monitor. `TradeManager` is the deterministic state machine, with users and two FIFO order queues.

### 3.2 Writes

1. `DidaTradeApp.populate/adduser/buy/sell` generates `sequence_number * 100 + client_id`, sends the same payload/ID to every replica and waits for one successful RPC reply. The normal app is sequential; different client processes can be concurrent.
2. `DidaTradeMainServiceImpl` applies the debug gate, creates a `DidaTradeCommand`, obtains the canonical record through `registerRequest`, wakes the selected loop and waits on that record.
3. Classic runs Phase 1 and then blocking Phase 2 for one instance. Multi prepares once per ballot and dispatches several asynchronous Phase 2 attempts. Fast prepares, sends ANY for its window, and each replica votes locally on its own oldest eligible client request.
4. Consensus messages contain **command IDs, not command payloads**. Acceptor handlers preserve promised/accepted state and notify learners. Learners count separate acceptors in one ballot/instance; a successful concrete Phase 2 certificate also lets the coordinator decide locally.
5. The coordinator executes only a continuous decided prefix. It waits if a decision's payload has not arrived. Processed IDs consume their log position without another execution.
6. `executeRequest` performs the domain action and increments the applied version under the domain monitor, moves the record to processed, and wakes response waiters. Write replies attach the current applied version; it can include later operations already executed before the handler constructs its reply.
7. The app uses the first reply and raises its causal watermark. Different replicas may complete the request at different times without returning inconsistent cached write success/failure results.

Important assumption: every correct replica eventually receives the client payload. There is no payload-fetch RPC. If a client process dies during a partial broadcast, consensus on an ID alone does not supply its payload to other replicas. This is an explicit liveness limitation of the current delivery design, not a demonstrated Paxos agreement violation (`DidaTradePaxos.proto`; all three prefix executors).

### 3.3 Balance and console

`DidaTradeApp.balance` broadcasts a minimum watermark with a 12-second RPC deadline. The service applies the debug gate and calls `readCausalBalance`; it neither uses `RequestHistory` nor wakes consensus. The read waits on the domain monitor, checks cancellation periodically and returns wallet plus version from one locked snapshot.

Console `ballot` calls `newballot`. Fast acknowledges without waiting for a decision; Classic/Multi may wait until the completed-ballot counter reaches the requested ballot. In an idle system the latter can remain pending until a command is decided. This acknowledgement behavior is implemented, but the assignment gives no finite idle acknowledgement deadline. Debug commands remain outside the client/Paxos debug gate. `activate` acknowledges without controlling the coordinator and must not be presented as a VP II implementation.

## 4. Step-by-step assessment

### 4.1 Step 1 — Classic Paxos

`MainLoop.processEntry` (lines 42–140) processes instances sequentially. `prepareAcceptor` atomically raises the global promise and captures the accepted snapshot under state-to-log lock order. `PhaseOneResponseProcessor.onNext` counts distinct promises and retains the highest accepted ballot/value. Phase 2 uses Schedule A quorum 2; lower ballots and conflicting same-ballot values are rejected by `acceptPhaseTwo` and `PaxosLog.accept`. Learned decisions do not overwrite the acceptor's separate accepted snapshot.

Classic retries failed attempts after 500 ms when still leader with pending work. It retains one proposed value per ballot/position, because a timed-out RPC may still execute remotely. `testClassicPhaseTwoTimeoutKeepsTheSameProposal` passed on the audited revision and asserts identical retry values. Timed retries do not elect a new leader. Manual ballot changes are the intended mechanism when the selected leader fails.

`RequestHistory` and the processed-ID check prevent duplicate write execution. `recordLearn` separates ballot certificates and uses an acceptor set to avoid duplicate Learn votes. Classic's learner assumes honest configured senders; it does not validate membership as strictly as Fast. The normal production transport satisfies that assumption. Forged messages/Byzantine faults are not assignment requirements.

Assessment: core phase/safety mechanisms are implemented and have supporting evidence. No generated conflicting decision was found. Shared defects AUD-01/02, Learn-delivery AUD-03 and incomplete final-version integration coverage prevent a complete sign-off. Earlier totally ordered/cached balances have been replaced globally by Step 4; see §4.4 and AUD-05.

### 4.2 Step 2 — Multi-Paxos

`MultiPaxosMainLoop.prepareLeadership` (lines 115–172) reuses preparation for the same ballot, recovers the highest accepted entry per log position and creates a hole set up to the highest known decision/acceptance. Ballot numbers are independent of log positions. `startProposal` tracks `(ballot,instance)` attempts and does not wait for one attempt before starting another. This is actual Multi-Paxos overlap, not Classic with a renamed loop.

`processCompletedPhaseTwoAttempts` allows an old-ballot successful certificate to decide after a newer preparation and prevents an old-ballot failure from scheduling an old retry. Sends are atomically guarded against a changed ballot or already decided position. `executeDecidedPrefix` retains its cursor across leader changes, skips processed IDs and pauses for holes/payloads.

The common promise and accepted-snapshot machinery is appropriate for fixed Schedule A. No dynamic acceptor-set correctness is claimed. Hole filling uses actual eligible pending requests; it does not manufacture a sentinel command. The finite-workload case with insufficient eligible requests around recovered/duplicated values should be tested before asserting unconditional recovery progress. This is recorded as a coverage concern, not a demonstrated reachable production defect.

Assessment: intended preparation reuse, instance allocation, recovery and concurrency are present. AUD-04 is a source-established retry defect. Much of the production Multi composite test was not reached after the obsolete balance assertion, and no focused final-revision test proves overlap or accepted-value recovery during leadership changes.

### 4.3 Step 3 — Fast Paxos

`FastPaxosMainLoop.run/prepareLeadership/openNextInstances` prepares the initial ballot before clients arrive and opens a window of four positions. ANY is an authorization field, never an accepted command or a decision. `proposePendingRequests` runs on all acceptors, selects pending requests in local arrival order, reserves IDs locally and votes directly. `getNextFastInstance` prevents voting in a later unvoted position before earlier authorization arrives.

Fast `recordFastLearn` counts distinct configured acceptors separately by position and ballot. It decides only with four identical votes. It declares collision only when `maxVotes + missingVotes < 4`; silence alone does not justify advancement. Collision callbacks publish events; the loop checks the instance is undecided and atomically advances only the current ballot. Leader notification failures retry the same ballot.

The production configuration is `N=5`, `Qf=4`, `Qr=4`:

- Two Fast decision quorums intersect in at least `4+4-5=3` acceptors.
- Recovery and a decision quorum intersect in at least `4+4-5=3` acceptors.
- The required triple intersection is nonempty because `Qr+2Qf=12 > 2N=10`.
- The recovery forced-candidate threshold is `Qr+Qf-N=3`, matching Class 04 slide 20 (`N-2f'` with `f'=1`).

`FastPhaseOneResponseProcessor` freezes a quorum of distinct matching promises, groups entries by position, retains the highest accepted ballot, preserves any value meeting that threshold and otherwise chooses a deterministic candidate from the highest ballot. `startRecoveredProposals` sends concrete choices with quorum 4, preserving the same quorum family. Conventional `ScheduleB.quorum()==3` is not used for production Fast decisions. `PhaseTwoResponseProcessor` relies on one unary reply per separately targeted acceptor; its generic response counter is not itself a reusable Byzantine certificate validator.

Schedule B keeps leaders rotating over IDs 0–2 while acceptors/learners include 0–4. The supplied clarification changes acceptor count, not explicitly the leader schedule; retaining the original three leaders is defensible and not flagged as a defect. It should be revisited only if an additional professor message explicitly changes proposer rotation.

All seven `FastConsensusRegressionTest` methods passed. Five launch real five-replica clusters; the other two verify configuration rejection and the dump-comparison helper. Collision integration injects concrete Phase 2 requests to create acceptor votes rather than relying on naturally timed concurrent client arrivals. `FastLocalProposalTest` separately exercises real local selection with controlled transport. This evidence is substantial but does not prove arbitrary contention progress, cross-ballot exhaustive safety or post-dispatch Learn reliability.

Assessment: Fast quorum and recovery logic satisfy the supplied clarification and reviewed course rule; tested collision/failure/order scenarios pass. No Fast agreement defect was established. Shared domain defects and AUD-03 remain, while Step-4 causal coverage is separate.

### 4.4 Step 4 — Causally ordered balance

Relevant sources: `DidaTradeMain.proto`; `DidaTradeApp` write methods and `balance`; `DidaTradeMainServiceImpl.balance`; `DidaTradeServerState.executeRequest` (lines 350–395), `getAppliedVersion` and `readCausalBalance` (397–430).

The dependency is a scalar **count of distinct executed replicated operations**, not a ballot, a raw log position or a vector clock. Every first execution increments it, including failed domain actions and DUMP; duplicate log positions do not. Startup population is common initial state and does not increment it. Local balance reads do not increment it.

Why the count can represent the relevant observed history: if all replicas execute the same decided sequence in order and suppress duplicate IDs consistently, their first-execution sequences are identical prefixes. A version of `k` therefore names the same first `k` distinct executions on every replica. Duplicate log positions mean this is not necessarily log position `k`. A replica whose version is at least the client's watermark has applied the entire observed prefix, including other clients' operations observed indirectly through a previous balance. A vector clock is unnecessary for one totally ordered write history.

The client raises its watermark after populate, adduser, buy, sell and balance replies, including a false domain result. It propagates the watermark in every later balance. Only the reply actually consumed by the application is used; unconsumed late replies are not independent application observations. The collector stops collecting after return. The app uses a sequential request flow, so the non-atomic `causalVersion` variable is not currently shared between concurrent request methods.

The read and version snapshot share the same monitor as state changes and version increments. `wait` releases that monitor so consensus execution can advance; `notifyAll` and a 100 ms cancellation check unblock readers. Write replies obtain a version after their canonical response is ready, so their version cannot precede their own first execution. It can conservatively include later executions.

Writes do not carry `min_version`. This is **not by itself a causal-order defect** in the present design: a fresh write submitted after an observed executed prefix cannot be inserted into the already decided prefix; all writes go through the same log. Reads require the explicit dependency because they bypass that log. This reasoning depends on fresh, globally unambiguous request IDs and the consensus/prefix invariants, and still needs a client-level read→write→read experiment.

Balance retransmissions are new local observations, with potentially different results. Returning the old cached balance is not required by Step 4 and would conflict with treating these as current local reads. All protocol modes now use this local path; the consensus implementations remain separate. Keeping historical ordered reads as a selectable feature is a scope choice for later comparison, not an automatically missing mandatory Step-4 feature.

Missing evidence: no checked-in test sets `min_version`, checks `applied_version`, drives the real app watermark or verifies dependency waiting across replica changes. The previous isolated causal check mentioned in project context was not rerun and is not counted as current audit evidence. The implementation is therefore **implemented but insufficiently tested**, rather than proven incorrect or VERIFIED end to end.

## 5. Correctness and validation issues

### AUD-01 — Explicit population does not initialize the requested state

- **Severity:** MEDIUM. **Affected:** baseline/shared domain, all steps.
- **Expected:** assignment §2: the initialization command creates users `[0,n)` with wallet and stock `n`.
- **Actual:** state construction first calls `populate(10)`. A later explicit `populate(n)` attempts to add existing IDs, ignores `add_user` failures and returns true. Thus the normal first client initialization with `n!=10` does not establish the described state.
- **Files/methods:** `DidaTradeServerState` constructor, lines 88–89; `core/.../TradeManager.java:19–35`, `populate/add_user`.
- **Evidence:** compiled-method evaluation reproduces normal constructor initialization followed by the requested operation: `populate(10); populate(5); balance(0)` returns **10**, not 5. User 9 also remains present. The constructor confirms that this starting state occurs in production. No replicated RPC reproduction was run.
- **Reproduction:** start a fresh normal deployment; issue `populate 5`, then `balance 0`. Source and direct domain evaluation predict the observed balance 10 despite the populate success reply.
- **Recommended correction:** make the first explicit initialization match the specification; resolve whether to remove eager default population or define a compatible explicit initialization path. Do not assume that arbitrary later populate commands must erase existing orders/users: repeated initialization semantics are not fully specified. Check for a professor clarification before choosing that policy.
- **Coverage problem:** `ConsensusRegressionTest.checkMode` checks `populate(12)` only through new user 11, which can hide incorrect values for existing users 0–9; on the final revision that assertion is not reached anyway.

### AUD-02 — Percentage calculations overflow for valid integer balances/stocks

- **Severity:** MEDIUM. **Affected:** baseline/shared domain, all steps.
- **Expected:** `buy(u,50)` with wallet 100,000,000 reserves 50,000,000 currency units; the item price is one (§2).
- **Actual:** multiplication occurs in 32-bit `int` before division. `100000000 * 50` overflows to 705,032,704; the order reserves **7,050,327**, leaving **92,949,673**. The same calculation occurs for sell stock.
- **Files/methods:** `core/.../TradeManager.java:59` (`sell`) and `:81` (`acquire`); `User.withdraw/removeStock` receive the already incorrect quantity.
- **Evidence:** direct evaluation of compiled `add_user(42,100000000,100); acquire(42,50); balance(42)` produced 92,949,673. The RPC accepts integer cash/stock and the specification gives no smaller maximum that excludes this positive value.
- **Reproduction:** add a fresh user with this wallet, buy 50%, then read balance; no seller is needed because currency is reserved when the buy order is placed.
- **Recommended correction:** use a sufficiently wide intermediate for multiplication/division and make the supported numeric bounds explicit. Review accumulation overflow separately; this reproduction proves percentage overflow, not every possible numeric failure.

### AUD-03 — A terminal Learn RPC failure can permanently strand learning

- **Severity:** HIGH. **Affected:** Steps 1–3; indirectly Step 4 dependencies on a lagging replica.
- **Expected:** after a transient transport failure and restored communication, correct replicas should be able to learn already accepted/decided work without requiring unrelated future requests or a manually forced recovery ballot.
- **Actual:** `notifyLearners` sends each vote once. `CollectorStreamObserver.onError` only decrements a collector counter; it retains no retry obligation. - **Reproduction scenario to verify:** let acceptors vote on position `i`, cause enough Learn calls to a healthy learner to terminate with a transport error before that learner collects a certificate, then restore transport. ## 8. Cross-cutting and architecture concerns

1. **Payload and decision delivery are separate obligations.** Canonical IDs protect execution identity, but a replica can know an ID without its command. Prefix blocking is correct; absence of payload fetch and Learn replay bounds the supported failure model. See §3.2 and AUD-03. No persistence/restart or Byzantine tolerance is claimed.
2. **Ordered execution is the basis of causal versions.** The applied-operation count is safe only while replicas share one ordered first-execution history. Future parallel state-machine execution or inconsistent duplicate filtering would invalidate it. No such redesign is recommended; retain this invariant and test it (§4.4).
3. **Protocol-specific coordinators are usefully separate.** Shared log/history/transport do not require merging their distinct preparation, proposal or retry policies. The Multi retry correction can remain local. No cosmetic refactoring is justified by this audit.
4. **Threading boundaries are mostly deliberate.** Acceptor promises/snapshots are atomic under state-to-log lock order; domain updates/read snapshots use the manager monitor; Fast callbacks only queue events and wake the worker; collector completion callbacks run outside its monitor. No concrete deadlock cycle was established in the reviewed normal flows. This does not substitute for directed timing tests.
5. **Client IDs and lifecycle assumptions matter.** IDs 1–99 are checked by the app, and sequence-derived IDs are unique only for distinct concurrently used client IDs without sequence reuse/overflow. Request histories are in memory. Client-ID reuse after restart and server restart recovery are unsupported rather than tested guarantees (`DidaTradeApp.main_loop`, request methods; `RequestHistory`).
6. **Step-4 reads have weaker semantics by design.** They may differ across clients/replicas when no dependency is supplied; that is permitted causal behavior. A test expecting identical unconstrained reads from lagging replicas would be invalid. Writes still follow the common log, so total-order guarantees for writes are not intentionally relaxed.
7. **Scope exclusions remain explicit.** Schedule C metadata does not implement state transfer; activation ACK does not implement VP II. Neither is silently promoted to an implemented feature. The completed-ballot counter is sufficient for the current fixed-set framework but is not a proof of transferable dynamic membership (`updateCompletedBallot` explicitly warns about this).

### 11.1 AUD-03 — Fixed shared Learn delivery recovery

**Status: FIXED / VERIFIED in the reproduced Classic, Multi and Fast scenarios.**

Production file: `server/src/main/java/didatrade/server/DidaTradeServerState.java`.
Relevant members: retry constants/executor and `pendingLearns:33–40`; `notifyLearners:278–306`; `sendNextLearn:310–350`.

The existing one-shot notification path now retains the original immutable `LearnRequest` in a small per-learner `LinkedHashSet`, guarded by the `pendingLearns` monitor. The set preserves queued order and deduplicates identical pending `(acceptor, instance, ballot, value)` notifications. There is no new delivery class or generic framework.

Delivery rules:

1. The first queued notification starts an asynchronous Learn RPC. Further pending notifications to the same learner queue behind it, while other learners remain independent.
2. Each local acceptor-to-learner link has **at most one active RPC or scheduled retry**. Concurrent notifications and repeated Phase 2 acceptance cannot start overlapping delivery chains for that link.
3. An `onError` leaves the vote at the queue head and schedules its identical request again after **250, 500, 1,000, then at most 2,000 ms**. The cap bounds delay/traffic; it does not limit the number of retries and discard a still-undelivered vote.
4. An `onCompleted` removes the acknowledged vote. An empty queue is removed from the map; otherwise the next head is sent immediately with its initial backoff reset.
5. When the source channel is shut down, the callback or next scheduled attempt removes that learner's backlog and stops sending. A delayed task can live until its capped delay expires, but it does not reschedule or retain the backlog after observing shutdown.

All states in one JVM share one lazily started daemon scheduled executor. Its tasks only launch asynchronous RPCs; no timer thread blocks on a learner response and no thread is created per vote/attempt. Healthy deliveries do not create timer tasks.

The original outer forked context is retained, and each outbound attempt also runs inside a forked context, including attempts initiated from timer/callback threads. Cancellation of the originating RPC cannot cancel the vote delivery. Learn calls use wait-for-ready in every mode; terminal errors, not channel-readiness waiting, trigger the explicit backoff.

**Learn's original no-deadline behavior is preserved.** During review, an initial two-second Learn deadline was removed: repeatedly timing out a frozen handler would create additional cancelled handlers blocked in the existing freeze gate. A frozen learner now retains one in-flight call on each link; unfreeze resumes it and drains the queued votes. Phase 1/2 retain their existing two-second deadlines. This choice is tested, not merely assumed.

Vote identity is never reconstructed from current ballot state. A pending old-ballot notification remains the original acceptor vote even after a higher promise. Neither error handling nor retry scheduling changes ballots, signals a collision, elects a leader, or changes a quorum. Existing learner distinct-acceptor accounting makes redelivery harmless, including the case where the receiver processed the vote but its acknowledgement was lost.

**Why bounded backoff is sufficient here:** the confirmed failure is a terminal unary-call error for an already accepted vote, while source state remains alive and the destination eventually resumes service. Retaining and resending that vote provides the missing certificate evidence. Existing receiver idempotence handles uncertain delivery. One queue per link additionally bounds concurrency under a large backlog, which separate free-running retry chains would not do. Persistence, a new consensus instance, state transfer, election or a general reliable-broadcast framework is unnecessary for this correction.

### 11.5 Remaining limitations and mandatory stop

These fixes provide eventual delivery **when a failed call receives a terminal error, source state remains alive and the destination eventually accepts/acknowledges a subsequent call**. An in-flight call with no terminal event is retained rather than timed out; this preserves frozen-request behavior and prevents retry-handler accumulation. The system does not claim a finite recovery deadline for arbitrary silent failures or an infinitely slow/non-acknowledging learner.

The cap bounds active attempts, timers and retry rate, **not the number of distinct accepted votes awaiting a permanently unavailable learner**. Such outstanding votes remain intentional delivery obligations while the source channel is open; acknowledgements or deliberate channel shutdown release them. Continuous accepted work during permanent unavailability can grow the backlog, just as the existing in-memory log/history grows. Dropping that backlog or guaranteeing bounded storage would require an explicit failure/retention/state-replay design beyond these localized corrections.

Per-link serialization can delay later notifications behind a slow head, while other learners and consensus proposal overlap continue independently. No throughput improvement is claimed. Persistence/process restart recovery, dynamic membership, state transfer and Step 5 remain excluded.
